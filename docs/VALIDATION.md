# Validation and limits

The 0.3.7 integration preview preserves KuiDaXElaina's original commits and combines their receive-progress/settings work with our experimental sender and update checker. All **234 protocol tests** pass. Receive UI regression tests cover unrelated connection failures, matching upload failures, a separate pending approval, and stale recovery timers; settings/localization, update selection and setup tests also pass. The full three-patch series applies to two independent clean pinned source archives, and the combined backend, Windows app and 3.49 MiB setup compile. Received/progress, Settings and Send screens were rendered and inspected using demo data. This combined build has not yet been installed or tested against the iPhone, and no new release was published. The source packaging script now includes the complete patch series; a fresh full kernel/driver corresponding-source archive has not been generated in this integration check.

Outgoing discovery initially found no iPhone announcements despite an AWDL peer being visible. The Windows frontend now broadcasts a bounded Bluetooth LE AirDrop wake-up signal during searches. Windows reported successful advertising on the development PC, and an integrated search discovered a recipient approximately five seconds later. Actual delivery to the iPhone remains pending.

The first wake-up build still failed to rediscover the same device on subsequent searches. A transport fix now clears per-search suppression and queued discovery results before each browse. A regression test confirms that the same phone can be reported in a new search while the local receiver remains excluded. All 232 protocol tests pass from a clean patched upstream source tree. Discovered recipients now appear in a visible list instead of being hidden in a dropdown.

The owner then confirmed discovery but outgoing attempts received TCP connection-refused errors before any consent request. The frontend now starts a fresh BLE wake beacon for sending and keeps it active until completion, cancellation, or the five-minute deadline. Only opening the initial TCP connection is retried (three attempts); no accepted transfer or upload is retried automatically. The new transient-refusal regression brings the protocol suite to 233 passing tests. Delivery to the real iPhone still awaits confirmation.

The next hardware test established TCP and completed discovery, but no iPhone approval prompt appeared. The sender now declares a transfer ID and file-transfer type in `/Ask`, repeats the same ID in `/Upload`, sends total source bytes, uses the DVZip media type when negotiated, and includes keep-alive/user-agent headers. A separate wire-level test validates the serialized request and upload headers against a inspecting TLS peer (234 protocol tests total). Sender logs now distinguish writing `/Ask` from receiving its response, and unanswered approval exchanges time out after 90 seconds. Real-iPhone approval and delivery remain unconfirmed.

Further diagnostics: the installed .NET sender sent `/Ask` and waited without a response, despite its TCP payload being acknowledged. An independent Python TLS/plist probe received a complete HTTP 200 `/Ask` response with receiver-session fields. `/Discover` independently identified the target as Albin's iPhone with `IsAirDropable=true`. A direct .NET fresh-connection probe still stalled; its client certificate was sent, and Python independently decoded its binary plist successfully. A 12-digit sender ID alone did not resolve the .NET probe. A candidate controller change now starts a transfer directly with `/Ask` (matching OpenDrop), with regression coverage, but that change is not a demonstrated hardware fix and has not been installed. The receiver/app stopped during diagnostics, ending further live comparison. No successful iPhone file delivery has been observed.

The outgoing prototype adds four passing controller tests (231 protocol tests total): real loopback TLS transfers preserve selected file bytes, receiver rejection writes no files, unknown peer IDs cannot trigger a connection, and invalid/duplicate selections are rejected. Discovery cancellation is exercised before sending through the same transport. These checks establish local protocol behaviour, not compatibility with a receiving iPhone. The Send page was rendered and reviewed; a real iPhone discovery, approval, and upload remains pending.

Earlier versions received single photos, three-photo batches, HEIC/PNG files, and Safari links from an iPhone 16 Pro Max on iOS 27.0. The protocol suite now has **227 passing tests**, the bridge relay regression test passes, and OWL had **52 passing tests**. The setup engine provisioned a clean Ubuntu runtime on the development PC. The 0.3.4 suite includes a regression test in which a new transfer request starts while an earlier discovery connection remains open. After the bridge update, the same iPhone sent three photos successfully, including a 2 MB HEIC that uploaded in seven seconds; one still had a short wait before sending. The development PC's owner reported that SwooshDrop worked after a full Windows restart with the 0.3.6 app.

Discovery can still be intermittent, especially with a 2.4 GHz-only adapter. Sustained throughput, large files, Live Photos, metadata fidelity, prolonged and repeated reboot use, experimental adapters, and fresh second-PC installation need testing. A successful setup on the development PC does not establish universal compatibility. Builds are currently unsigned.
